# Shared Canvas file attachments and assignment submission release

Status: local implementation; production, target ChatGPT tool refresh and real user flows are not verified. Feature switch defaults off. This candidate is the separately scoped release requested on 2026-09-21; no test submission or teacher message is authorized by feature development.

## User flow and discoverability

The user may provide a file and request sending/submission, or request that ChatGPT generate a file and send/submit that actual artifact. The Canvas Skill, Study Skill, MCP initialization instructions and dedicated tool descriptions route these requests. ChatGPT's native `openai/fileParams` metadata identifies `file` as a file reference, with required `download_url`/`file_id` and optional declared `mime_type`/`file_name`.

Skills describe capabilities and user-intent boundaries, not a mandatory dialogue or fixed sequence. The agent composes available tools according to the request; account checks, limits, target binding and receipts are enforced by Core. File generation remains the client's existing artifact capability.

New tools: `upload_canvas_file`, `submit_assignment`. Existing `send_message` and `reply_message` accept optional `attachment_ids`; no parallel attachment-only tools. Existing text-only calls remain valid. Tool discovery is separate from permission to call them. No extra agent confirmation is required after the user explicitly authorizes an unambiguous action; native client approval requirements still apply.

## Boundaries reviewed in this candidate

- Both Berkeley and Hanyang share the same Canvas services and tools, bound to the authenticated Core identity and fixed school host. Each uploaded file receipt additionally binds the Canvas user identity, target assignment and purpose.
- The user explicitly approved one Study authorization for all enabled capabilities, including existing connections. The legacy `canvas.read` OAuth identifier is retained for compatibility and is now the single Study account grant. Retired granular scope names are accepted during authorization and normalized; tools no longer request them. Consent and Skills describe enabled capabilities plainly. Authentication, account isolation, explicit operation intent and truthful write annotations remain. `CANVAS_COURSEWORK_WRITES_ENABLED` and the existing message switch control release availability, not separate user grants.
- Individual `online_upload` plus optional comment, or plain `online_text_entry`. No quizzes, group assignments, external tools, grading, on-behalf submissions, assignment creation or attendance changes. Verify publication, user-specific locks, dates, formats, current attempt and remaining attempts. An expected-attempt mismatch requires resolving whether another attempt is intended. LMS remains authoritative for enrollment and late-work acceptance.
- Files are fetched from exact inspected HTTPS CDN origins configured in `CHATGPT_FILE_ORIGINS` (default `https://files.oaiusercontent.com`). Generated ChatGPT files also support the observed `https://chatgpt.com/backend-api/estuary/content` endpoint, requiring exactly one nonempty `sig` and one `id` matching the native file reference. Other ChatGPT paths remain rejected even if its origin is added to configuration. Downloads omit credentials, never follow redirects, and retain the 20 MiB streaming limit, no local persistence and no raw audio/video. Unrecognized hosts are reported by origin only, without signed paths or queries, and rejected before any LMS upload; inspect real client handoff evidence before adding an exact CDN origin, never a wildcard.
- Direct multipart Canvas upload: notify, transfer bytes with the provider's parameters and file last, then verify the Canvas confirmation. Rename duplicates; explicitly set `submit_assignment=false` and never pass a URL-upload parameter. Upload credentials/parameters stay in memory. Upload storage defaults to the school origin; `CANVAS_UPLOAD_ORIGINS` (Hanyang) and `CANVAS_BERKELEY_UPLOAD_ORIGINS` accept only separately inspected exact HTTPS origins and never share storage permissions across schools. No Canvas PAT goes to storage. Confirmation is restricted to the school's `/api/v1/files/:id[/create_success]` path. Redirects elsewhere are rejected.
- Upload success is distinct from sending/submitting. A final assignment receipt needs a matching POST result and fresh own-submission read with expected attempt, account, assignment, type, files/text and comment. Attachment delivery verifies a new matching sent message and attachment IDs without marking Inbox read.
- Additive schema 10: `canvas_write_receipts` with fingerprints, minimal file metadata and receipts; no raw file bytes, temporary URLs, message bodies or submission text. Atomic claims prevent concurrent duplicate requests and overlapping pending/unknown assignment submissions. Signed source URL refresh does not change upload identity. Unknown results are never retried automatically; unknown target locks deliberately require manual record reconciliation before administrative resolution. Uploaded files may remain after a final failure; no cleanup/delete API is added.
- An upload that fails before its byte transfer (ticket request, destination or parameter checks) sent nothing to LMS storage; its claim is released and the same request ID may be retried. Text submissions are confirmed by comparing the visible text Canvas stored, because Canvas re-serializes sanitized HTML (quotes, entities and spacing). Unknown upload, submission and message outcomes are logged with the failing stage, error code, account and request ID, never content or credentials.
- Administrative resolution, only after the person has inspected the LMS records: in the Core container run `node dist/cli/resolve-write-receipt.js --list`, then `--user <account UUID> --request <request_id> --outcome applied|not_applied`. `applied` keeps that request ID permanently answered without inventing a receipt; `not_applied` removes the claim so the assignment or file target can be used again. Pending claims younger than 15 minutes are refused because they may still be running.
- Canvas has no atomic conditional-submit API: a simultaneous submission made directly in the LMS after the preflight read cannot be prevented by Study's local ledger. Post/read-back attempt verification detects a mismatch and reports unknown, never repeats the operation.

## Release and rollback

Run the repository release check and prepare an immutable candidate. Inspect production version/schema and configuration, obtain fresh source/config/database backups, then use `core-release.sh prepare` with explicit policy `coursework-writes-v10`. That policy accepts only the exact additive 9 → 10 ledger migration; prior image must boot on the migrated database copy. Keep both new and old images and the saved configuration. Rollback restores the old image/config and retains the current database, including receipts; do not restore an old database over later data.

Enable the switch only in the reviewed production release. Verify each school's real upload storage before adding any exact origin. Refresh the online private Study app's tools and Skill availability in the target ChatGPT account; local caches do not count. Verify that both existing school connections work without separate read/write reauthorization. Public/internal health, tool discovery, permission checks, actual chat attachment handoff, generated-file handoff and final user-requested LMS receipts are distinct evidence tiers. A build or mocked provider test proves none of those live tiers.
