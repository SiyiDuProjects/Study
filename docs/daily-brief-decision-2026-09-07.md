# 汉阳每日课程提醒：决策建议

2026-09-07。讨论稿，供决定是否实施。此次只新增本文，没有修改插件、定时任务或生产服务，也没有向任何人发送消息。

**建议先做插件里的一个短 Skill，使用现有通用读取接口，并在她实际使用的 Chat 定时任务里验收。专用日报接口暂时不做；只有完整检查的实测成本或稳定性证明有需要时，再增加小范围的数据聚合。**

这一建议收窄了上一轮直接提出的“Skill + 日报接口”。原因是需求已经明确：她需要每天很快知道上什么课、要完成什么、要准备什么，以及哪些安排发生变化。当前首先需要解决的是必要信息的覆盖、行动表达和实际送达，而不是增加报告基础设施。

**判断依据与证据边界。**

本次回看了“新建每日课程检查”“检查学习计划功能”“温欢学校事项提醒”的相关记录，检查了当前仓库的 Skill、Canvas/LearningX 工具契约、文件链接实现和既有 QA 记录，并核对了 OpenAI 官方 Skill 与定时任务文档。

历史对话记录显示，最近一次计划为韩国时间每天 08:00，在 Chat 中新建；此前已明确要求简化检查流程，且出现过“文件接口尚未准备好”的过时固定文案及某次结果没有正常显示。这里是在引用历史记录，没有读取计划后台核验当前启用状态，也没有把过去的课程提醒当作今天仍然有效的课程事实。

当前源码已有分页、分来源错误结果等改进，但本会话暴露的部分工具参数仍没有 cursor；例如 list_assignments 和 list_modules。已有优化交付文档也区分了本地修改、安装包和生产发布。因此不能凭本地源码就宣布她的定时任务已经能完整读取所有内容。

**她收到的信息，应直接对应行动。**

每天的内容回答三件事：今天怎么上课；今天和近期有什么必须做；需要提前知道或准备什么。资料入口附在相应课程或任务后面，不额外罗列“文件”栏目。

| 内容 | 呈现原则 |
| --- | --- |
| 今日课程 | 每一节都列；给实际时间、地点或线上入口。临时改动就写“改为”，一般不同时重复原时间、原教室、原安排。 |
| 今日截止、仍需处理的逾期事项 | 全部列出，明确课程、动作、时间和入口。已提交、免交或确定完成的事项移除；仍需修改重交的单独保留。 |
| 近期任务 | 普通事项默认看未来三天；考试、大作业、分组、买教材等需要准备的事项，在首次获知时就提醒，不机械等到三天内。 |
| 非作业形式的要求 | 视频出勤、课前问卷、带材料、入群、群内提交、教师要求回复或修改，都按实际动作处理。 |
| 新通知、反馈和成绩 | 只把会改变安排、需要采取行动，或值得她知道的重要变化写出来。普通发布动态和无变化分数不每天复述。 |
| 不确定信息 | 只说她需要知道的影响，如“今天教室有冲突，请出门前确认”，并给对应来源；不输出技术错误堆栈。 |

精简靠合并同一件事、去掉套话和已完成事项。当天必做事项不能因为“最多六条”被截断。五到八行可以是普通日子的阅读目标，不是硬上限。空栏目直接省略。

同一项“明天截止的作业”昨天提醒过，今天更接近截止时仍应出现；这属于必要提醒。相同公告在三个平台各占一行才是应当去掉的重复。看到过、提醒过、她读过、她做完了，是不同状态。

下面仅是虚构的展示样例，不是实际课表或待办；正式输出的资料、提交、通知文字应嵌入已验证的来源链接：

> 9月8日 周二｜韩国时间
>
> 今天 10:00–12:00 A课，教学楼302；14:00 B课改线上，使用课程里的 Zoom 入口。
>
> 今晚23:59前：A课交第一周作业；B课还有一段出勤视频未完成。
>
> 明天C课要带A4纸，课前下载第2周讲义。

**“不遗漏”需要完整检查，不能等同于把所有原文发给她。**

| 检查来源 | 为了找到什么 | 容易漏掉的情况 |
| --- | --- | --- |
| 有效的正式课表及学期范围 | 今日固定课次 | 只显示有新公告的课程；周末直接跳过补课或截止事项 |
| 本学期各课公告、LearningX Board、相关教师讨论回复、Canvas Inbox | 临时改课、要求、延期和补充说明 | 只看“过去24小时”或“未读”；旧帖子修改；上周通知今天生效 |
| 所有本学期课程的作业、测验及自己的提交情况 | 今日/近期截止、逾期、无日期要求、重交 | 只查今天有课的课程；只查未来任务；Planner 勾选完成被当成实际提交 |
| LearningX 周学习及相关项目详情，必要时交叉查看考勤集合 | 视频、出勤期限、问卷及学习活动 | 考勤集合为空就推断没有视频；缺少完成状态就推断未完成 |
| 课程日历、当前模块及其关联页面/附件 | 考试、补课、课前资料、正文里的额外任务 | 把 Calendar 当正式课表；只读附件标题就断言文件里没有要求 |
| 已授权的学校邮件来源 | 邮件独有的课程通知和学校必办事项 | 把邮件视为 LMS 的重复副本，整类过滤 |

所有本学期课程都要做通知和待办检查；今日课程要重点核对实际上课安排。不能为了减少正文，提前把其他课程或无截止日期的要求从检查中排除。

发布日、更新日、生效日、截止时间必须分开。不能从“9月8日”自行补出“23:59”，也不能从本周存在录播视频推断当天整节课取消。必要时查看通知或附件原文；语义不明确就用短句保留不确定性。

初次启用时需要建立本学期的有效课程规则和未完成事项基线。日常至少复查这些仍有效的规则、所有开放任务以及新的或变化的信息。没有可靠修改时间或持久比较基准时，应保守复读可能影响本期安排的原文，不能仅凭标题、未读数或上次聊天印象跳过。如果这些保守读取过慢，再以实测为依据增加缓存或聚合。

没有完成状态的外部表单、群内任务，不能被系统宣布“已完成”，也不能武断写成“未交”。可以写成“课前需填写，完成情况暂无法核实”。她明确说已做完后，可作为本人确认使用，同时保留其与平台状态的区别。第一版不承诺跨新对话永久记住这种确认。

课堂口头要求、Kakao 群和未连接的校务系统是额外来源。已有可访问转录在确实有用时可以补充，但不能依靠关键词搜不到就判定没有要求，也不建议每天从头总结全部课堂录音。仅靠 Hanyang 插件无法保证看见未接入来源中的信息；若以后要覆盖，可接入相应授权来源或让她把该条通知转入同一对话。

**邮件需要有归属，跨来源去重不能靠猜。**

历史邮件提醒中出现过课程开始时间、教师变更同意表、线上周学习要求和学校必办事项。这说明邮件并非完全冗余。这些例子仅用于分析来源分布，没有在本次重新核验其具体内容和完成状态。

从她的体验看，相关课程信息最好在一份晨间提醒里合并。若现有 Chat 同时能读取正确账号的授权邮箱，可以在最终呈现层合并，底层仍分别使用 Hanyang 和邮箱连接，不把邮箱凭据放进 Study Core。

若目前做不到，保留现有邮箱提醒作为补充；不要先关闭它，也不要仅按“LMS 自动转发”整类忽略邮件。只有核对到课程、事项、生效日期与关键要求确实相同，才能认定重复；邮件多了地点、期限或必须填写的表单，必须保留新增部分。未共享可靠结果的两个计划不能声称已经做到全局去重。

本次不建议为合并一份提醒新建邮件服务、同步数据库或投递系统。直接发给她还取决于她实际使用的对话/账号和已授权的接收渠道，不能把在你的对话生成成功等同于她收到。

**为什么先选 Skill，以及什么时候才值得加接口。**

| 方案 | 解决的问题 | 没有解决的问题 | 建议 |
| --- | --- | --- | --- |
| 继续只改定时提示词 | 最快调整格式和检查说明 | 规则随计划分散，容易保留旧文案；依赖上下文 | 不作为长期唯一维护位置 |
| 插件中的短 Skill + 现有接口 | 我们维护检查与呈现标准，手动和定时可复用，方便随插件更新 | 不保证读取和文字绝对一致，仍需验证分页、语义和运行结果 | 第一阶段优先 |
| 小范围数据聚合接口 + Skill | 固定重复读取、分页、去重和来源状态，减少模型编排 | 不能自动理解所有教师文字；一个接口也可能截断或遗漏 | 在实测暴露编排问题后采用 |
| 服务端完整生成、定时、存档、推送 | 接管更多运行生命周期，可建立长期状态 | 增加模型调用、提示词维护、调度、存储和投递责任 | 当前需求不值得直接做 |

Skill 建议只在“每日课程检查/晨间提醒”请求中启用。一般“明天几点上课”“这份作业怎么做”继续走现有 Canvas/Study 流程，避免每问一个简单问题都触发全课程扫描。日报 Skill 应只集中维护来源覆盖、必要信息筛选、短输出和异常处理，不复制全部工具目录。

Core 继续负责身份绑定、权限、分页、原始状态和可靠错误语义。这些基础能力不能靠增加 Skill 字数补偿。新增聚合接口的触发条件应是可观察的问题：完整读取连续无法在约定窗口完成、跨课程分页反复中断、相同查询大量重复，或在相同输入下持续漏掉必查来源。仅仅“能少调用几个工具”不是充分理由；一个大响应同样可能超时、截断，且学校侧请求量未必减少。

若确实需要聚合，应复用现有客户端，返回来源事实、必要原文、已检查范围和未完成部分；不要直接返回一句“今天没有事”。即使聚合层进行分页，也需要时间/体积上限与明确的续读或部分完成状态，不能无限抓取，也不能静默停止。

精确跨日去重、旧通知未来生效、本人确认的外部待办如果成为日常痛点，可再增加小量持久状态：来源ID、内容版本、有效日期、未解决状态与引用。保存生成结果不等于确认通知已送达，更不等于她已完成。当前先不创建报告档案库或通用任务系统。

OpenAI 官方文档把 Skill 定义为可复用的指令、资源及可选脚本，并建议需要确定性行为时使用代码；定时任务文档也建议把持久指令放在任务提示词或附加 Skill 中，先在正常对话测试，再检查前几次定时运行。[Skill 指南](https://learn.chatgpt.com/docs/build-skills)；[定时任务指南](https://learn.chatgpt.com/docs/automations)。

**文件下载已实现，交付方式应按实际链路判断。**

当前源码和本会话工具契约显示：get_file 返回文件元数据和临时下载地址；当前代码的地址有效期为15分钟。访问地址后，Core获取原文件字节并以附件下载响应返回。get_file本身没有直接返回ChatGPT持久文件附件；该下载路由也未将文件写入持久文件库。

用户确认此前已下载过文件，已下载的副本不会因地址过期而失效。但此次未核实这些副本的保存位置或定时对话的访问能力，不能承诺直接跨运行复用。日报可以使用实际可访问的文件；是否直接交付文件或提供下载地址，应以目标Chat的实际能力验收，不预设只能发链接，也不预设已有持久附件。相关实现见 [工具返回内容](../apps/core/src/mcp/canvasTools.ts:32) 与 [文件下载响应](../apps/core/src/app.ts:251)。

**最小的质量要求，应验证她会不会漏事。**

以下是建议的验收场景，此次没有执行新测试或模拟一次真实日报：

| 场景 | 必须得到的结果 |
| --- | --- |
| 正常两节课，没有新通知 | 两节都出现，课程安排清楚，省略空栏目 |
| 上周发布、今天生效的调课 | 正确修改今天这门课；不影响另一门课或下周 |
| 今天无课，另一门课作业今晚截止 | 仍然提醒截止事项 |
| 第一页都是已完成任务，第二页有未完成任务 | 能续读并保留该任务；不可输出空待办 |
| Planner 勾选完成，但作业未提交 | 依实际提交证据判断；不被勾选隐藏 |
| 考勤列表为空，周学习里有必看视频 | 报告视频要求并读取完成证据 |
| 老通知被修改，延期只写在补充说明或教师回复中 | 保留正确期限；冲突不能静默覆盖 |
| 附件里写了“下次课前填写问卷” | 读取需要的附件内容，提取动作；不能只列文件名 |
| 同一通知出现在公告、Inbox、邮件 | 合成一项，新增要求和不同动作仍保留 |
| 当天有九项必须处理的任务 | 全部列出，可合并表达，不按条数删掉 |
| 某课程读取失败或列表未读完 | 给出已知结果，并以一句话说明相关缺口；不写“没有任务” |
| 在她实际使用的对话中打开资料 | 能打开与该课程和任务对应的正确文件 |

落地前，先核对真实 Chat 任务可见的插件版本和接口参数，再用相同证据重复生成，检查课程时间、截止、完成状态和必做事项是否一致；文案不必逐字一致。候选流程可与完整人工核对的样本对照，记录遗漏、误报、重复、耗时和链接可用性。这里的人工核对用于验收，不应变成她每天的额外工作。

另外必须看一次完整的定时链路：任务触发、读取结束、正文出现、接收者能看到。历史记录已经出现过“运行了但没有正常显示”；仅测试手动生成无法排除这一层问题。官方文档允许网页任务使用该对话可用的连接工具、Skill 和插件，但不访问本地文件夹，因此本地新增一个 Skill 文件不等于她的 Chat 已安装并能调用它。[定时任务指南](https://learn.chatgpt.com/docs/automations)。

每天08:00的结果是检查时点的快照，不包含08:10才发布的临时通知。若之后要求连这种变化也及时提醒，就需要另外决定补查或事件触发；改变报告格式或新增日报接口无法解决频率问题。本次不创建额外监控计划。

只有成功完成必要范围的检查且没有应提醒内容时，才可以安静不推送；任务记录应能区分“检查成功无事”与“未运行/检查失败”。来源失败且影响今日安排或截止判断时，仍应有简短提醒。

**可以直接拿来讨论的短工作说明。**

下面是草案，不是已安装 Skill，也不是已修改的定时提示词。工具名称与参数应使用实际已发布契约。

> 使用 Hanyang Study 为她生成韩国时间的每日课程提醒。先读有效正式课表，再检查本学期所有课程的通知、任务与完成情况；重点核对今天课程的临时安排、视频出勤和所需资料。结合相关公告、LearningX、Inbox、日历及必要的页面或附件，保留早先发布但仍有效的要求，不能只查今天有课的课程或过去一天的新消息。使用已授权邮箱时补充独有信息，并合并重复事项。
>
> 告诉她今天怎么上课、必须做什么、近期要准备什么。逐项给明确动作、已知时间和最合适的来源入口；资料跟随对应课程。今日截止和仍需处理的逾期事项全部保留，普通近期事项默认看未来三天，需要提前准备的更早提醒。移除已完成事项，省略空栏目和无变化的背景介绍。
>
> 读完必要分页；完成情况以对应来源的证据为准。无法确认、来源冲突或读取不完整时，用一句话说清实际影响。正文尽量一屏，但不为缩短删掉必做事项。不要把平台已读、提醒过或Planner勾选当成实际完成，不做任何课程或消息写操作。

这一草案仍需在目标 Chat 里验证；单靠这段文字无法承诺零遗漏。最合理的先后顺序是：明确必要信息 → 验证接口完整性 → 形成一屏提醒 → 验证真实定时与阅读体验 → 只有实测需要时再添加聚合或持久状态。
